## 목표와 범위

Labtop Intel GPU에서 컨테이너의 실제 H.264 VAAPI 인코딩을 검증하고, 브라우저 합성 WHIP→MediaMTX→VAAPI H.264/AAC→LL-HLS의 단일 품질 경로를 확인한다. 호스트의30프레임 합성 h264_vaapi preflight는 성공했지만 컨테이너·브라우저 경로의 증거는 아직 없다.

- 새 실험은 `experiments/media-vaapi/`에 격리한다. 기존 CPU 실험과 제품 Go/Flutter 동작을 유지한다. 기존 웹 helper와 hls.js를 재사용하며 복제하지 않는다.
- 별도 Docker 프로젝트 `wbb-media-vaapi`, 전용 파일·컨테이너만 사용한다. 기존 서비스·Caddy·DNS·방화벽·k3s·호스트 패키지는 변경하지 않는다.
- 모든 host publish는127.0.0.1만 사용한다. 관리/RTSP/HLS/WHIP를 외부에 공개하지 않는다. SSH local forwarding 및 MediaMTX TCP ICE 후보를 이용한 검증 경로를 제공한다. 이는 실제 외부망 UDP/NAT/TURN 검증을 대신하지 않는다.
- MediaMTX1.21.3 고정, FFmpeg/Intel 드라이버가 실제 동작하는 컨테이너를 사용한다. 기반 이미지 digest·패키지 버전·검증 환경을 기록한다. 드라이버 부재/장치 접근 실패 때 CPU로 조용히 대체하지 않는다.
- decode는 필요 시 소프트웨어, 인코딩은 명시적으로 h264_vaapi다. 해상도는 최대1280×720, 원본보다 확대 금지, H.264/AAC·30fps/GOP60을 유지한다. 소스/출력 경로는 분리한다.
- start/stop은 소유 자원만 다루고 초기화 실패에도 잔여 프로세스/컨테이너가 남지 않게 한다. 임의 프로세스 kill·prune·기존volume삭제 금지. 새 실험용 원격 디렉터리만 전송·사용한다.

## 완료 기준과 검증

1. 컨테이너에서 GPU 장치·VAAPI 초기화·실제30프레임 인코딩 성공, H.264/AAC ffprobe 확인. 호스트 성공과 구분한다.
2. 1280×720·세로1080×1920·작은640×360 입력에 대해 양축 제한·무확대와 양수/짝수 치수를 확인한다.
3. Chrome 합성 WHIP 송출, TCP ICE 선택, 실제 LL-HLS part 진행·재생 시간/프레임 증가·오디오 비영을 독립 관측한다. 단순 파일 인코딩만으로 이 항목을 통과시키지 않는다.
4. 종료 시 원래 encoder PID/시작 시각 소멸, source/output 비활성, 새 part 중단을 관측한다. API 오류와 조회 불가는 PASS가 아니다.
5. 검증 후 실험 컨테이너·helper·SSH forward를 정리하고 기존 서비스가 유지됨을 확인한다.

실제 PC/모바일·두 기기 청취·Safari·TLS·외부망·장시간 부하·ABR는 계속 미검증이다. 이 후속의 성공으로 티켓02/03/04를 완료하거나 선행 조건을 우회하지 않는다.
