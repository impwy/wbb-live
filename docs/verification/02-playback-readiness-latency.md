# 재생 준비 상태·지연 검증

기준 커밋은6cb0b2a, 브랜치는 `work/media-device-acceptance`다. 구현은 지정 대체 Codex, 독립 검증은 조정 Codex가 담당했다.

## 변경 전 재현

변환 영상이 준비되기2초 전에 HLS 요청이 들어가404와 manifestLoadError가 발생했다. 영상 준비 후 별도 Chrome에서 정상 재생했다. 송출이 없는8090 화면에서도 재생·소리 버튼이 활성화된 것을 독립 확인했다.

사용자가 보고한 큰 실제 화면 캡처 지연은 아직 재현하지 못했다. 조정자가 측정을 시작했을 때 사용자 송출이 종료돼 지연값을 얻지 못했다.

## 최종 독립 검사

| 검사 | 결과 |
| --- | --- |
| 기존 CPU 브라우저 회귀 |83/83 통과, skip0 |
| 준비 상태 브라우저 fixture |11/11 통과 |
| 실제 Caddy HTTP 경계 |16/16 통과 |
| 실제 HTTPS Chrome 송출·영상·오디오·종료 |14/14 통과 |
| 별도 송출·시청 탭의 준비·오류·재시작·일시정지·라이브 이동 |12/12 통과 |
| 송출 중 관측한 FFmpeg PID |송출 종료 후 사라짐 확인 |
| 명세·표준 독립 재리뷰 |잔여 확정 결함0건 |

fixture의 BFCache 검사는 합성 pagehide/pageshow 이벤트이며 실제 브라우저 뒤로 가기 인수를 대신하지 않는다. fatal 오류 후 재시도 검사는 소스 정리 및 재생 위치 진입을 확인한다. 해당 단계만으로 새 디코딩 프레임 증가까지 증명했다고 주장하지 않는다. 일반 재생의 프레임·오디오는 별도 실제 경로 검사와83항목에서 확인했다.

## 지연 관측과 한계

최종 독립 합성 측정은 publish 시도→첫 master 약7.06초, media/part 준비 약7.08초, 준비 후 첫 프레임 약0.26초였다. 약8초 동안5개 유효 표본에서 canvas→수신 video readback은1.08~1.53초, HLS live edge 지연은0.777~0.830초였다. 실제 카메라·화면 캡처·물리 디스플레이 지연 및 장시간 안정성을 포함하지 않는다.

`liveSyncPosition-currentTime`은 목표 재생 위치와의 편차이며 live edge 지연은 `hls.latency`다. 초기 입력 분석 옵션 시험의6.42초는 기준6.25~7.31초 범위여서 개선 근거가 없었다. 인코더·MediaMTX 설정은 바꾸지 않았다. 사용자의 실제 큰 지연이 해결됐다고 판단하지 않는다.

## 적용과 자원

조정자가 검토 코드와 동일한 app.js를 embed해8090 helper만 교체했고 실제 HTTP 응답의 바이트 일치를 확인했다. 기존 미디어 컨테이너는 재시작하지 않았다. 새로고침 후 준비 상태, 비활성 재생·소리 버튼, 명시적 라이브 이동, 지연 관측값을 사용할 수 있다.

독립 검증용 Compose 프로젝트·볼륨은 정리했다. 전체 컨테이너 목록 비교는 false였으며, 같은 시각 다른 testcontainers/ryuk의 자동 제거 이벤트가 있었다. 기존 CPU MediaMTX·transcoder·Redis3개의 동일 ID와23시간 이상 uptime을 별도 재확인했다. 사용자의 기존 서비스가 재시작됐다고 추정하지도, 전체 목록이 동일했다고 기록하지도 않는다.

실제 사용자 화면의 지연 재시험, 아이폰 및 외부망 인수는 남아 있다. 외부 검증 환경은 사용자 요청에 따라 종료된 상태다.
