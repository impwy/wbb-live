# WBB 초기 설계안

> 이 문서는 초기 후보 기록이며 현재 설계를 대체하지 않는다. 이후 사용자 결정으로 Go·Flutter Web·JWT/OIDC·LL-HLS·CDN 미사용·WBB 전용 LGTM이 선택되었다. 최신 설계는 `../docs/design.md`와 `../.scratch/wbb-live/spec.md`를 따른다.

작성: Codex / 2026-11-06. 상태: 요구사항 분석 및 기술 후보. 기술 스택·배포 환경·세부 API 계약은 아직 확정하지 않았다.
사용자 제공 요구사항과 이 문서의 제안 정책을 구분한다. 구현 담당은 GLM이며 아래 내용은 아직 전체 구현 지시가 아니다.

## 범위와 우선순위

필수 범위는 인증, 방송 정보 CRUD, 브라우저 PC·모바일 송출, 비로그인 시청, 서버 소유자 권한 검증, 실제 송출 종료, 영속 저장, README와 접근 가능한 서비스다.
댓글·도네이션·녹화는 필수 기능이 실제 기기에서 통과한 뒤 검토한다. 대규모 추천·검색·구독·채팅은 필수 요구사항으로 추가하지 않는다.

## 구조 후보

```text
PC/모바일 브라우저 ── HTTPS ── 프런트엔드 / 백엔드 API ── PostgreSQL
       │                              │
       │ WebRTC                       │ 송출 권한 발급 / 종료 제어
       └────────── 미디어 서버(SFU) ───┘
                         │
                         └── 이벤트 통지 → 백엔드 상태 반영
```

- 프런트엔드 후보: React + TypeScript. 목록, 상세 시청, 가입·로그인, 방송 관리, PC/모바일 송출 화면.
- 백엔드 후보: Spring Boot. 인증, 소유권, 방송 상태, 미디어 서버 제어를 한 애플리케이션의 모듈로 분리한다.
- 저장소 후보: PostgreSQL과 스키마 마이그레이션. 사용자·방송·송출 세션을 영속 저장한다.
- 미디어 후보: LiveKit 기반 WebRTC SFU. 브라우저가 직접 송출하고 시청자는 구독한다. 미디어 전송을 일반 API 서버에 통과시키지 않는다.
- 배포: 서비스와 API를 같은 출처로 제공하는 구성을 우선 검토한다. HTTPS/WSS, 외부 네트워크 연결, TURN 경로, DB 볼륨·백업을 포함한다.
- LiveKit Cloud와 자체 운영 중 어느 쪽을 쓸지는 비용·기존 서버·토큰 무효화 동작을 확인한 후 결정한다. 외부 리소스는 아직 생성하지 않는다.

## 송출 및 시청 설계

### PC

1. 사용자의 시작 버튼 클릭으로 화면 선택을 요청한다. 화면 선택 전에 오래 걸리는 비동기 작업을 넣어 사용자 활성화 조건을 잃지 않도록 한다.
2. 화면/탭과 공유 오디오를 받고 마이크를 별도로 획득한다. 공유 오디오 트랙이 실제로 존재하는지 확인한다.
3. 마이크와 공유 오디오를 각각 발행하고 시청자가 두 트랙을 모두 재생하는 방식을 먼저 검증한다. 단일 믹스 트랙이 필요하면 Web Audio로 합성하는 방식을 검토한다. 요구사항은 두 소리의 동시 전달이며 단일 트랙 자체를 요구하지 않는다.
4. 미디어 서버의 발행 성공을 확인한 뒤 LIVE로 전환한다. 실패하면 부분 획득한 트랙과 생성한 송출 세션을 정리한다.
5. 공유 중지 이벤트와 종료 버튼을 같은 종료 절차로 연결한다. 본인 미리보기는 음소거해 되먹임을 줄인다.

### 모바일

- 화면 공유 대신 카메라와 마이크를 획득한다.
- 카메라 권한 거부, 장치 없음, 점유 상태를 구분해 안내하고 실패 시 획득한 트랙을 정리한다.
- 화면 잠금·백그라운드 전환 시 지속 송출을 보장한다고 안내하지 않는다. 끊김을 감지하고 복구 또는 종료 상태를 반영한다.

### 시청

- 비로그인 사용자도 목록·상세를 읽고 수신 전용 연결 권한을 발급받는다.
- 시청자의 미디어 권한은 구독만 허용한다. 영상·음성·데이터 발행 및 방 관리 권한을 부여하지 않는다.
- 음성 자동 재생이 차단되면 재생/소리 켜기 버튼을 제공한다. 프런트엔드 표시만으로 송출 권한을 제어하지 않는다.

## 인증 및 데이터 모델 후보

- 인증 후보: 서버 세션과 HttpOnly·Secure 쿠키. 변경 요청의 CSRF 보호와 로그인 시 세션 교체, 로그아웃 시 서버 세션 무효화를 적용한다. 비밀번호는 검증된 비밀번호 해시 알고리즘으로 저장한다.
- `users`: ID, 로그인 식별자, 비밀번호 해시, 표시 이름, 생성 시각.
- `broadcasts`: ID, 소유자 ID, 제목, 설명, 생성·수정·삭제 시각, 동시성 제어용 버전.
- `broadcast_sessions`: ID, 방송 ID, 시작마다 새로 생성한 미디어 방 식별자, 상태, 시작·종료 시각, 종료 사유, 버전.
- 방송 정보와 송출 회차를 분리해 재방송 시 이전 이벤트가 새 회차 상태를 덮어쓰지 못하게 한다.
- 등록 시 소유자는 서버가 인증 정보에서 결정한다. 수정·삭제·시작·종료·송출 권한 발급 모두 서버에서 소유자를 조회해 비교한다.
- 방송 목록에는 방송자의 비공개 식별 정보, 비밀번호 해시, 송출 토큰이나 서버 비밀을 포함하지 않는다.

## 방송 상태 및 종료

제안 상태: `READY → STARTING → LIVE → STOPPING → ENDED`; 시작 실패는 종료 사유를 기록하고 `ENDED`로 정리한다. 방송 중이 아닐 때의 표시와 재시작 정책은 API 계약에서 명시한다.

- 서버가 상태 변경을 책임진다. 시작 요청만 받았다는 이유로 LIVE로 표시하지 않는다.
- 방송당 활성 회차는 하나로 제한하고 중복 시작·종료 요청을 잠금 또는 조건부 갱신으로 처리한다.
- 종료 시 새 송출 권한 발급을 먼저 차단하고 미디어 서버의 발행자/방 종료를 요청한다. 실제 제어에 실패하면 STOPPING 상태와 재시도 작업을 유지한다.
- 브라우저는 모든 캡처 트랙과 연결을 닫는다. 서버는 이를 신뢰하는 것에 그치지 않고 미디어 서버의 실제 송출을 종료한다.
- 종료 후 이미 발급된 토큰으로 재접속·재발행할 수 있는지 검증한다. 토큰 TTL만으로 기존 연결이 종료되거나 토큰이 즉시 취소된다고 가정하지 않는다.
- 이벤트 서명 검증, 중복 이벤트 무시, 회차 식별자 및 상태 전이 검증을 적용한다.
- 송출자 이탈, 이벤트 누락, 서버 재시작 시 미디어 서버 상태를 조회해 DB를 조정한다. 연결 단절 유예 시간은 추후 계약에서 고정한다.
- 방송 중 삭제 정책 후보: 409로 거절하고 먼저 종료하도록 안내한다. 삭제 후에도 내부 종료·감사 기록을 유지한다.
- 방송 중 로그아웃 정책 후보: 송출 종료를 요청하고 로컬 캡처를 정리하며, 세션은 무효화한다. 종료 실패 시에도 서버 재시도를 지속한다.

## 브라우저 제약과 검증 대상

- 화면 공유 오디오 지원은 브라우저·운영체제·공유 대상으로 달라진다. `systemAudio: include`만으로 시스템 오디오가 제공된다고 보장할 수 없다. PC는 우선 데스크톱 Chrome/Edge의 탭 공유 + 탭 오디오 + 마이크 경로를 실제 기기에서 검증한다.
- 공모 요구사항은 “탭 소리 또는 시스템 소리”이므로 모든 운영체제에서 시스템 전체 소리를 지원한다고 약속할 필요는 없다. 화면 캡처와 두 음원 전달을 실제로 입증하고 README에 지원 범위를 적는다.
- 휴대폰의 카메라·마이크 접근은 실제 접근 가능한 HTTPS 환경에서 검증한다. Android Chrome과 iOS Safari는 검증 후보이며, 실제 테스트 전에는 지원 확정으로 표시하지 않는다.
- 공유 음원이 없는 경우 마이크만 송출되는 상태를 숨기지 않고 재선택 방법을 안내한다.
- 실제 기기·소리·외부 네트워크 검증은 브라우저 자동 테스트나 모의 미디어만으로 대체하지 않는다.

근거: [MDN getDisplayMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia), [MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), [LiveKit 미디어 발행](https://docs.livekit.io/transport/media/publish/), [LiveKit 권한 및 토큰](https://docs.livekit.io/frontends/reference/tokens-grants/). 확인일: 2026-11-06.

## 구현 순서와 완료 관문

| 순서 | 작업 | 다음 단계로 넘어가는 기준 |
| --- | --- | --- |
| 1 | 기술 스택·실제 기기·배포 후보 확인, 송출 기술 검증 | PC의 두 음원 및 모바일 카메라·마이크를 다른 기기에서 수신 |
| 2 | 인증·DB·방송 CRUD·소유자 검사 | 권한표와 재시작 영속성 검사 통과 |
| 3 | 인증된 송출·비로그인 시청 통합 | 서버 송출 권한과 미디어 권한 거절 검사 통과 |
| 4 | 종료·중복 요청·연결 끊김·상태 복구 | 실제 송출 종료, 이전 권한 재사용 거절, 상태 복구 확인 |
| 5 | 화면 완성·서비스 운영 설정·README | 외부 접속과 평가용 로그인, 두 기기 시나리오 통과 |
| 6 | 선택 기능 | 필수 기능의 수정 여유와 제출 준비를 확보한 경우에만 진행 |

제안 일정: 11/06~07 요구사항·기술 검증, 11/08~11 인증·CRUD·송출 통합, 11/12~14 종료·권한·장애 처리, 11/15~17 실제 기기·운영 환경 검증, 11/18 필수 범위 동결·README, 11/19 최종 확인·제출. 확정 일정이 아니며 필수 시나리오가 지연되면 선택 기능을 제외한다.
